## B03 invitation and activation

Use WorkOS AuthKit **staging** for a disposable invitation flow. The admin form accepts email only. Keep Verity's installation entitlement and signed offline interval in SwarmTracker storage, separate from AuthKit identity.

1. Issue an application invitation for the exact email. Associate invitation ID, target email, expiry, and local pending activation ID. WorkOS documents both application-wide and organization invitations; choose application-wide unless an organization is explicitly created.
2. At acceptance, bind the returned verified user email and invitation ID to the pending record, collect required Name and visible optional Organization in Verity, then issue the installation entitlement. Do not treat entering an email or opening the link as activation.
3. Test wrong recipient, reused/expired invitation, relaunch, offline signed interval, device replacement, and revocation. WorkOS says invitation acceptance shortly after email delivery may itself verify email; otherwise its ordinary verification flow applies. Inspect `email_verified` and events rather than assuming every click has identical treatment.
4. Use staging's separate keys, users and webhooks. Test with example-domain accounts where an email is not meant to be delivered; use a controlled real test inbox only for actual delivery acceptance. No customer invitation is authorized here.

Sources: https://workos.com/docs/authkit/invitations ; https://workos.com/docs/authkit/email-verification ; https://workos.com/docs/authkit/environments ; https://workos.com/docs/reference/authkit/user

## B06 provider sign-in investigation

**Gemini API:** Prototype documented desktop OAuth against a test Google Cloud project, with consent screen and authorized test user. The Google quickstart uses a desktop client and application default credentials for a testing environment; production needs a deliberate credential design. Store tokens locally outside configuration and exports, send one governed request, verify revocation and account/project billing source. A Google consumer sign-in does not establish API entitlement. Sources: https://ai.google.dev/gemini-api/docs/oauth ; https://ai.google.dev/gemini-api/docs/billing

**Claude API:** Evaluate the official `ant auth login` browser flow for a dedicated Claude Console workspace and profile. The CLI documentation supports local development and scripting with refreshable OAuth credentials, `ant auth status`, `ant auth logout`, and bearer-token API calls. Do not copy tokens into Verity records or confuse this Console path with Claude.ai subscription delegation. Test local token storage, real request, usage source, logout, stale credentials, and fail-closed dispatch. Sources: https://platform.claude.com/docs/en/cli-sdks-libraries/cli/authentication ; https://platform.claude.com/docs/en/cli-sdks-libraries/cli/scripting

**ChatGPT/OpenAI:** Keep the submitted Sign in with ChatGPT application pending until access and official eligibility are verified. Keep the ordinary OpenAI API key adapter separate. No implementation claim.

**Perplexity/Meta:** Research each official supported authorization and inference route before exposing sign-in controls. No inferred consumer-account delegation.

The B05/B07 external acceptance gate is one real authorized request with model/revision, task identity, consent and billing source, pre-dispatch policy, usage reconciliation, removal/revocation, and stale-state failure recorded. The local OpenClaw slice does not satisfy that external gate.
