# Local installation and update operations

This pilot uses offline activation and an operator-owned private issuance registry. The registry lists credential issuance and replacement history. An operator-entered acknowledgment or version report is not authenticated hardware identity or a live device attestation. Last contact is unknown until reported, and stale after 24 hours. A replacement code does not revoke its predecessor. An offline installation learns about revocation only after importing a newer cumulative signed issuer list; expiry still applies locally.

Set `VERITY_PILOT_REGISTRY` to the private registry path in an operator profile to show **Installation registry** from Installation & Runtime. Ordinary profiles do not expose the private registry. The view contains IDs, reported versions and status, never activation codes. The operator CLI accepts `registry`, `report`, and `authorize` operations in `tools/local_release.py`. It records allow or deny per installation, release and channel with immutable change events. An absent authorization denies an update. The issued activation code remains separately installation-bound and expires after its signed interval.

Build a release in a separate location and compute its directory digest. Sign a versioned manifest offline with `tools/sign_release.py`; its key must be an owner-only file outside the repository and package. Supply the corresponding public key via `VERITY_RELEASE_PUBLIC_KEY` to preview a local release in Setup, or pass it to `tools/local_release.py inspect`. The manifest binds release ID, version, artifact digest, macOS architecture and minimum OS, release channel, supported schema and release notes. This signature is an application-level publisher check, **not** Apple Developer ID signing or notarization. The current pilot remains ad hoc signed and cannot claim Gatekeeper acceptance.

The local install command requires a signed manifest, app directory, installation ID, profile, installed version, schema version, activation and publisher public keys, and matching registry authorization. It checks the local signed activation and imported revocations before preview and again before installation. `inspect` prints the approval phrase. Quit the target app, choose a **new** history directory outside both the target and its data profile, then run `install` with the exact approval phrase, target path, profile path and history path. The CLI checks the installed app's Info.plist version and registry authorization again. It stages and hashes the app, backs up the existing app and entire profile, journals the attempt, and replaces only the specified stopped target. A failure restores the previous app and profile; retain its journal and backup. Never point acceptance at the installed pilot. No automatic or silent install is provided.

An older release requires `--rollback` and a distinct explicit authorization for that release. Rollback is supported only when the existing profile schema is within the older release's declared supported schema. No schema-changing migration is currently supported: such a manifest is refused until a tested migrator exists. Restore a compatible profile backup before attempting an older binary; copying only the binary can leave an unreadable newer database. External running work and provider resources are outside the update installer.

For recovery, stop the app, inspect `outcome.json` in the selected history directory, compare the retained `previous.app` and `profile-backup`, and retry with a fresh history directory only after resolving the cause. An interrupted attempt before replacement is journaled as recovered. If power fails during the narrow filesystem switch, the staged directory and separate backups must be inspected by an operator; the installer does not claim crash-atomic transactions across directories. Keep the trust-record checkpoint separately from an exported history.
